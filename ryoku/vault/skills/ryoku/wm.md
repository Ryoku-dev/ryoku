# The window-manager seam

Ryoku supports Hyprland and niri through one provider contract. Learn the live
provider and its capabilities before suggesting a setting, action, config file,
or reload:

```bash
ryoku wm status
ryoku wm caps
ryoku wm state
ryoku wm config
```

- `status` names the detected provider, whether it is live, its workspace model,
  capabilities, and setting domains.
- `caps` prints the provider manifest as JSON. Treat every capability as a
  promise. If it is absent, do not offer the action or setting.
- `state` prints the current outputs, workspaces, windows, focus, and keyboard
  state with provider-issued ids. Round-trip ids unchanged.
- `config [name]` prints that provider's config directory, user-owned seeds, and
  generated files. Use `ryoku wm config hyprland` or `ryoku wm config niri` when
  asking about an installed but inactive provider.

Do not infer the running compositor from a process name, an environment
variable, or a config directory. A stale session can leave all three behind.
`ryoku wm status` checks that the provider is live.

## Actions stay neutral

Dispatch a live window-manager action through:

```bash
ryoku wm act <id> [args]
```

The ids describe intent, such as `window.close`, `workspace.focus`,
`output.power`, `session.exit`, or `input.touchpad`. They are public contracts,
not a passthrough to a compositor command language. Check `caps` before an
action whose capability may be absent. Shared shell, Hub, CLI, and QML code asks
for capabilities and actions. It never calls compositor IPC directly and never
branches on a provider name.

## What Ryoku owns

The repository payloads use each compositor's native language:

| Provider | Authored payload | Live entry | Generated by the provider |
|---|---|---|---|
| Hyprland | `ryoku/hyprland/`, Lua modules loaded by `hyprland.lua` | `~/.config/hypr/hyprland.lua` | `settings.lua`, `rebinds.lua` |
| niri | `ryoku/niri/`, KDL files included by `config.kdl` | `~/.config/niri/config.kdl` | `settings.kdl`, `rebinds.kdl` |

The payload and generated files are Ryoku's. Never hand-edit them. Hyprland has
one concern per Lua module under `ryoku/hyprland/modules/`. niri's top-level KDL
includes every file in override order; a missing include is fatal and the last
include wins. Its generated `rebinds.kdl` is the complete bind set because niri
has no unbind and rejects duplicate chords in one bind block.

A packaged update lays the shipped base down again, then overlays the sparse
user tree at `~/.config/ryoku/user_edits/`. A mirrored file there wins, but it is
a whole-file fork and no longer receives upstream fixes automatically. Prefer a
command, the Hub, or the last-loaded user file over a fork.

## Put user changes where the owner says

Before any edit, ask the same ownership code that `ryoku materialize` uses:

```bash
ryoku owner <path>
```

For raw compositor config, it points to files seeded once and then owned by the
user:

- Hyprland: `~/.config/hypr/user.lua`, loaded last.
- niri: `~/.config/niri/user.kdl`, included last.

The Hub is the first choice for keybinds and window rules. Use the raw files only
for config the GUI cannot express.

### Hyprland Lua

Add a keybind to `~/.config/hypr/user.lua` with the same `hl` API as the shipped
modules:

```lua
hl.bind("SUPER + SHIFT + T", hl.dsp.exec_cmd("kitty"))
```

Add a floating rule in the same file:

```lua
hl.window_rule({
    name = "float-mpv",
    match = { class = "mpv" },
    float = true,
})
```

Do not copy `modules/binds.lua` or `modules/window_rules.lua` merely to append a
rule. If a full shipped file truly must be owned, copy it to the mirrored path,
for example `~/.config/ryoku/user_edits/hypr/modules/binds.lua`, and remember
that `ryoku reset hypr/modules/binds.lua` returns it to Ryoku.

### niri KDL

Add a keybind to `~/.config/niri/user.kdl`:

```kdl
binds {
    Mod+Shift+T { spawn "kitty"; }
}
```

Add a floating window rule in the same file:

```kdl
window-rule {
    match app-id="mpv"
    open-floating true
}
```

Keep the block in `user.kdl`, after the generated includes. Do not edit
`rebinds.kdl`, `settings.kdl`, or fork `config.kdl` just to append a rule.

## Reload and prove the change

For Hyprland, parse the user file before asking the provider to reload:

```bash
luac -p ~/.config/hypr/user.lua
ryoku wm act config.reload
ryoku wm status
```

For niri, validate the full include tree. niri watches its config and reloads a
valid save itself:

```bash
niri validate -c ~/.config/niri/config.kdl
ryoku wm status
```

Then exercise the exact behavior. Press the new chord, open the matching app,
or inspect the affected workspace or window with `ryoku wm state`. A successful
parse or reload does not prove that a matcher or action did what the user asked.

## Never cross the seam

- Never edit a shipped or generated live file. Ask `ryoku owner` and use the
  path it prints.
- Never call `hyprctl`, niri IPC, or a provider binary from shared shell, Hub,
  CLI, or QML code. Use `ryoku wm act` or the Go `wm.Client`.
- Never name a compositor in a shared conditional. Add a capability or provider
  action instead.
- Never claim support because another provider has it. `ryoku wm caps` is the
  live answer.
- Never trust a config file merely because it exists. Use `ryoku wm status` for
  liveness and verify the behavior after reload.
